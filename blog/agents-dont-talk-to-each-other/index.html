[01] Design notes

How Noon’s agents learn about each other

When several AI coding agents work on one project, something has to keep track of all of them. In Noon, that’s Noon. Here’s how it works, why we built it this way, and what our own tests showed.

Snehith NayakNovember 20, 20268 min read

The short version #

  • Run two coding agents on one project and they will sometimes change the same code. That’s normal.
  • Noon gives every task its own copy of your project, so agents don’t overwrite each other’s work. The worst case is a merge you have to settle.
  • The agents never message each other. Noon watches what each one does and tells the others a sentence or two, only when it matters.
  • Before you merge, Noon tries the merge for you and tells you if it will conflict.
  • Noon never blocks an agent’s edit. We tried refusing an edit once, and it mostly didn’t change what the agent did.
  • In our own tests, Noon’s notes did not reduce conflicts. They did keep the agents, and you, informed. The details are below.

Two agents on one project will collide #

A peer-reviewed study replayed 107,026 pull requests written by coding agents that hadn’t been merged yet. 27.67% of them would have hit a merge conflict [1]. Bigger changes conflicted more often [1].

People have the same problem. In a peer-reviewed study of nine open-source projects, 16% of merges needed a person to fix a conflict. And of 399 merges that Git said were clean, 33% still broke the build or the tests [2].

So the real questions are what a collision costs you, and when you find out.

Each task gets its own copy #

Every task in Noon runs in its own copy of your project, on its own Git branch. Each agent works in its own copy. When two tasks change the same lines, you get a merge conflict at the end, not lost work. If an agent edits outside its copy, Noon tells it so. It doesn’t stop it [3].

This is how people have shared code for decades: copy, change, then merge. The other way is to lock a file while someone edits it, which makes everyone else wait. In the words of the Subversion book, "Locking may cause unnecessary serialization." [4]

One agent in our tests put it well, after Noon paused its edit: "My worktree is separate, so making this edit won’t overwrite its work. I’m going ahead and will flag the conflict." [5]

Not everyone agrees. One recent paper (a preprint, meaning it hasn’t been peer reviewed yet) put all its agents in one shared folder and checked every write as it happened. On one benchmark that beat giving each agent its own copy by 18.7 points [6]. Its agents split up one goal under one coordinator. Noon’s tasks are separate jobs that you start, and for those a merge at the end fits better.

Why the agents don’t talk to each other #

The obvious idea is to let agents chat: "I’m changing the login page, stay away." It doesn’t work well.

  • It doesn’t help. In a preprint called CooperBench, shown at an ICLR 2026 workshop, pairs of coding agents that could message each other succeeded about 30% less often than one agent doing both jobs. Their channels filled with "vague, ill-timed, and inaccurate messages". Messaging did cut merge conflicts. It didn’t make the work succeed more often [7] .
  • Claude Code and Codex can’t do it anyway. They have no shared channel to talk through [3].

So Noon is the one place the facts live. It watches every agent and tells each one what it needs to know.

An agent learns only the basics about the others: the other task’s name, which agent runs it, which files it changed, and when. A task’s name can be the first line of your instruction, or the title its agent gave the conversation, so those words do reach the other agents. Nothing else from their conversations does.

How Noon knows what each agent is doing #

Noon doesn’t ask agents what they plan to do. It watches what they do: the files they read and edit (Claude Code and Codex report these to Noon), every file written in each task’s copy, and what Git says each branch changed [3] .

That costs the agents nothing. And it’s what really happened, not what an agent said it would do.

What Noon tells each agent, and when #

Every word Noon adds is one the agent reads instead of your code. So Noon says very little, at four moments [3]:

  • When a session starts, if other tasks are running: a brief of at most 600 characters. It names the other tasks, the files you share with them, and whether a merge looks like it will conflict.
  • When you send a prompt: only what changed since last time. Usually nothing.
  • When the agent reads or edits a file another task changed: a note of at most 240 characters. For an edit, the note arrives just after the edit, not before. Noon won’t mention the same file again for ten minutes unless something changed.
  • When the agent asks: three read-only tools answer who is working where.

It’s fast: 95% of notes took 3 milliseconds or less, measured with ten tasks of 5,000 changed files each [3].

It isn’t free. In our tests, agents with Noon’s notes on used about 30% more input tokens (Claude Code 173k to 230k, Codex 70k to 91k). Almost all of that was text the model had already seen, sent again on one or two extra requests. Our test tasks were tiny, so the percentage looks bigger than it would on real work [5].

Noon tries the merge before you do #

Two tasks that touch the same file don’t always conflict. So Noon doesn’t guess. For any two running tasks that share code, and for each task against your main branch, it quietly runs the real Git merge and reports whether it would conflict [3]. You see the answer, and so do the agents.

One limit: a merge with no conflicts can still break your code. In a peer-reviewed workshop paper, changes that each passed their own tests failed together in 97% of runs on tasks built to show the problem. On 417 real pairs of changes to Django, it happened in 1 of 834 runs [8]. Noon’s check finds conflicts. It doesn’t run your tests.

Why Noon never blocks an edit #

Noon could force agents apart. It could make them claim files before editing, or block an edit that would collide. Neither worked out.

  • Claiming files. In one preprint, making agents claim files first raised the share of merges that went through from 65.6% to 96.7%. But 96.7% of the runs ended up taking turns, so the gain from running in parallel was gone. That study was 30 pairs of tasks by one author [9].
  • Blocking edits. We tried it. When an agent could choose where to make its change, Noon paused three of its edits. One agent changed course. Two made the same edit anyway. When you had asked for that exact edit, both paused agents made it again, as asked [5]. Blocking an edit you asked for is the wrong default.

There is a fair argument on the other side. One preprint says "at agent speed the warning arrives after the wasted edit", and plans who works where before anyone starts [10]. That needs every task’s files declared up front, which is the same trade as claiming them.

Did it work? What we found #

We ran Claude Code 2.1.319 and Codex 0.167.0 together on one small test project, 31 times; 30 runs counted. The two tasks could collide or not, depending on where each agent chose to make its change [5].

  • The agents paid attention. All 46 tasks that got Noon’s notes checked with Noon before editing. Noon’s brief asks them to [5].
  • Claude Code told you. Codex didn’t. Claude Code named the other task in its final message every time, 22 of 22. Codex never did, 0 of 24 [5].
  • Conflicts were not fewer. With Noon’s notes on, 8 of 17 runs ended in a conflict. With Noon silent, 4 of 7 did. That is no real difference [5] .
  • Habits won. Each agent mostly made its change where it usually does. A fresh note about the other agent’s change moved it in 4 of 8 cases [5].

These were small tests: a toy project, one-line tasks done in 15 to 60 seconds, two or three runs per setup, one model for each agent [5].

Here is what we changed afterward. Notes now cover edits made through shell commands. Noon’s answers include the last minute of edits. And "no changes yet" always says the other task is still working, and where. We didn’t build file claims or blocked edits [3].

What you see #

Codex never mentioned the other task, so you can’t count on the agents to tell you [5]. Noon shows you the same facts it gives them. The map shows each agent on the file it’s working on and outlines in amber the files two tasks share. For tasks that share code, you see whether they will merge cleanly. Each task’s row says how often Noon told its agent something.

What would change our minds #

Our tests were short. On real tasks that take minutes, the second agent would more often see the first one’s change before choosing. That is when Noon’s notes sometimes helped. If longer tests showed the notes changing nothing, or showed that claiming files is worth the lost parallel work, we would change course.

The bigger open problem is changes that merge cleanly and still break each other. In the Django study, telling an agent what the other, finished change did fixed 82% of runs (89 of 108). The researchers wrote that message, not an agent in the middle of its work [8]. It suggests telling agents what another change did, not just which files it touched. We don’t know yet whether that works outside a test.
