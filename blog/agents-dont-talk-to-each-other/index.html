[01] Design notes

Agents don’t talk to each other

Several coding agents on one repository need to know what the others are doing. We could have let them message each other. Here is why Noon tells them the facts instead, and what our own runs did and didn’t show.

Snehith NayakNovember 20, 202611 min read

Run two coding agents on one repository and sooner or later they change the same lines. Noon exists to run several at once, so we had to decide how each agent learns what the others are doing. The obvious answers are to let them message each other, to let them claim files, or to stop an edit that would collide. We built none of them.

This post is about what we built instead, why, and what our own runs showed, including the part that didn’t go our way. Each number names its source and what kind of source it is.

Agents collide #

Collisions aren’t rare. A peer-reviewed study replayed 107,026 agent pull requests that hadn’t been merged, and found that 27.67% of them would conflict [1]. Bigger changes conflict more: about 9.9% for pull requests with a median of 2 changed lines, nearly 30% around 25 lines [1]. The study covers agents’ unmerged pull requests only, so it doesn’t say whether agents collide more than people do.

People collide too. In nine open-source systems, 16% of all merges needed a person to resolve textual conflicts, and conflicts lasted 3.2 days on average. On the three systems with real test suites, 33% of the 399 merges Git called clean still broke the build or the tests [2].

So the question isn’t whether agents collide. It’s what a collision costs, and who finds out first.

A workspace and a branch per task #

Every Noon task gets its own Git worktree on its own branch, so each agent writes in its own copy and a collision costs a merge, not lost work. An agent that edits outside its copy is told so, not stopped [3].

Claude Code’s agent teams, an experimental feature that is off by default, give the same warning from the other side: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." [4]

Version control settled this argument for people long ago. The Subversion book weighs locking a file before changing it against copying, changing and merging: "Locking may cause unnecessary serialization." "Locking may create a false sense of security." Merging works because "most of their concurrent changes don’t overlap at all; conflicts are infrequent." [5]

In one of our runs, an agent whose edit Noon had held wrote: "My worktree is separate, so making this edit won’t overwrite its work. I’m going ahead and will flag the conflict." [6] It was right.

Not everyone agrees. A 2026 preprint routes every agent’s writes through one shared workspace so conflicts are caught as they are written, and reports beating a worktree per agent by 18.7 points on one benchmark [7]. Its agents divide one goal under one orchestrator; Noon’s tasks are separate jobs a person starts, which a merge suits better. It’s the strongest case against this decision we found.

Agents never message each other; Noon is the board #

With separate workspaces, each agent still needs to know what the others are doing. One way is to let them talk.

CooperBench, a preprint shown at an ICLR 2026 workshop, gave pairs of coding agents a channel to message each other. Working together, they succeeded on average 30% less often than one agent doing both tasks, and the channels "become jammed with vague, ill-timed, and inaccurate messages" [8]. Messaging did reduce merge conflicts there; it didn’t make the work succeed more often. A peer-reviewed study of seven general multi-agent frameworks, 1,642 annotated traces, found failure rates from 41% to 86.7%, and put 32.3% of the failures down to misalignment between agents [9]. Anthropic reports, from its own systems, that multi-agent setups use about 15 times the tokens of a chat, and that "most coding tasks involve fewer truly parallelizable tasks than research" [10]. A newer preprint on agents sharing one codebase found that a message channel "recovers only a small part of the performance, at an additional token cost" [11]. And a message from one agent to another is a way in for a planted instruction that then copies itself from agent to agent, a preprint showed [12].

There is a practical reason too: Claude Code and Codex share no mailbox.

So Noon is the one place the facts live, and each agent hears only from Noon. The idea is old. Research on people working together called it awareness, "an understanding of the activities of others, which provides a context for your own activity," and found it worked well when "provided and exploited passively through the shared workspace" rather than by sending messages [13]. A preprint on language-model agents found that a shared board "can be competitive" with the best multi-agent setups "and at the same time manage to spend less tokens", on reasoning and math tasks rather than code [14].

What one agent learns about another is short: the other task’s name, which agent runs it, the files it changed and when. A task’s name can be the first line of its instruction or the title its agent gave the conversation, so those words do reach the other agents. Nothing else of their conversation does.

Facts observed, not declared #

Noon doesn’t ask an agent what it intends to do. It watches what it does: the reads, edits and finished turns each agent’s hooks report, every file written in each task’s workspace, and what Git says each branch changed [3].

An agent asked to declare its plans has to remember to, spends tokens doing it, and can be wrong. A fact observed from the file system costs the agent nothing. Anthropic’s advice for building agents puts it from the other side: agents need "ground truth" from the environment at each step, and complexity should be added "only when it demonstrably improves outcomes" [15].

Say little, at the moment it matters #

Every token Noon adds is one the agent reads instead of your code. Chroma, a database vendor, tested 18 models in a technical report: "Even a single distractor reduces performance relative to the baseline" [16]. Anthropic’s guidance is to find "the smallest possible set of high-signal tokens" [17], and Codex’s own documentation warns that "context from multiple hooks and plugins adds up and can degrade model performance" [18].

So Noon speaks at four moments and is silent otherwise [3]:

  • When a session starts while another task of the project runs: a brief of at most 600 characters, naming up to three other tasks, the files this task shares with them, and their merge forecast.
  • When you send a prompt: only what changed since the agent was last told, usually nothing.
  • When the agent reads or edits a file that another task changed, touched in the last five seconds, or is forecast to conflict on: a note of at most 240 characters. It arrives with the tool’s result, so for an edit it comes just after, not before. The same file isn’t mentioned again for ten minutes unless what Noon would say has changed.
  • When the agent asks: three read-only tools answer who is working where, what is known about a file, and where a name lives.

The hook that prints these took 3 milliseconds for a note at the 95th percentile, 8 for a prompt and 29 for a brief, on ten tasks of 5,000 changed files each. It gives up at 500 milliseconds and prints nothing on any error [3].

It isn’t free. Codex carries the three tools’ definitions in every request, 1,529 characters, about 7% of the tool definitions it already sends; Claude Code carries only their names [3]. In our runs, tasks with Noon’s facts on used a median of about 30% more input tokens (Claude Code 173k to 230k, Codex 70k to 91k), nearly all of it a cached prefix sent again on one or two extra requests for Noon’s tools [6]. Those were one-line tasks, which overstate the share; the one or two extra requests are the real cost.

Try the merge ahead of time #

Two tasks touching the same file don’t always conflict, and file lists can mislead. A preprint that replayed 715 pairs of agent pull requests found that 79 of 167 textual conflicts (47.3%) happened although the files each pull request changed didn’t overlap, which the authors put down to how pull-request changes are measured. Replaying the merge itself took a median of 0.02 seconds: "when exact replay is cheap, verify everything." [19]

So Noon doesn’t guess. For each pair of running tasks that share a file or a dependency, and for each task against your branch, it runs Git’s own merge on the tasks’ current state, privately, and reports whether it would conflict [3]. That forecast is what the brief and the notes say, and what you see.

A clean merge isn’t a working one. In a peer-reviewed workshop paper, an agent’s code built on a helper another change had altered failed in 97% of runs on purpose-built Django tasks, although each change passed alone and they merged cleanly; but on 417 real pairs of Django changes, only one of 834 runs showed it [20]. Noon’s forecast is a textual merge. It doesn’t run your tests.

Tell, never block #

Noon could prevent collisions by force: make agents claim files before writing, or hold an edit that would collide. Claims buy fewer conflicts by giving up parallel work; holds, in our runs, mostly didn’t change the edit.

In a preprint, making agents claim files before writing raised the share of merges that integrated from 65.6% to 96.7%, but it "serialized 96.7% of executions, including 93.3% of clean cases," and the results "do not establish useful wall-clock parallel speedup" [21]. That was 30 task pairs, three seeds and one author. Another preprint’s gate "de-overlaps a median 91.7% of labeled scope collisions at 65.0% makespan inflation", in a replay rather than with live agents [19].

The case against telling is real too. One preprint argues that "at agent speed the warning arrives after the wasted edit" and plans disjoint scopes up front instead, which in its simulation cut merge conflicts from 13 to 0 [22] . Two more preprints found agents pass over what they’re given: agents surfaced a warning signal in 0 of 100 trials over SSH [23], and agents on Terminal-Bench found a planted solution in 79–81% of runs but used it in only 37–50% [24] . Planning up front needs every task’s scope declared before it starts; that is the claims trade again.

We tried holding edits ourselves. When an agent could choose where to make its change, Noon held three of its edits once (all Codex); one changed course and two made the same edit again. When the person had asked for the edit, both held agents made it again, as told [6]. Holding the edit you asked for is the wrong default, so Noon tells and never blocks.

What we measured, and what it didn’t show #

We paid for 31 runs of two real agents, Claude Code 2.1.319 and Codex 0.167.0, on one small repository; 30 were scored [6]. Two tasks started within about a second of each other, with instructions that collide or not depending on where each agent makes its change.

  • The agents read what Noon told them. All 46 told tasks called Noon’s tools before editing; the brief asks them to [6].
  • Claude Code told you; Codex didn’t. Claude Code’s final message named the other task in 22 of 22 told tasks; Codex’s in 0 of 24 [6].
  • Conflicts were no rarer. With Noon’s facts on, 8 of 17 runs ended in a conflicting merge. With Noon silent, 4 of 7 did. No measurable difference [6].
  • Habits won. Where each agent made its change followed its own habits more than Noon’s facts. A fresh fact about the other’s change moved the agent in 4 of 8 cases [6].

The limits matter as much: a toy repository, one-line tasks finished in 15 to 60 seconds, two or three runs a setup, one model each and no project instructions [6]. For people, showing developers each other’s parallel changes left fewer conflicts in the code they checked in [25]; for agents, our runs didn’t show that.

What we changed because of it: edits made through shell commands now get their note too, Noon’s answers include the last minute of edits, and "no changes yet" always says the other task is still working, and where. What we didn’t build: claims and held edits [3].

You see the same facts #

Codex never mentioned the other task, and Claude Code sometimes warned of conflicts that didn’t come [6], so you stay the place collisions are settled. Noon’s map shows each agent as a token on the file it’s working on, rings in amber the files two tasks share, and shows each pair’s merge forecast; each task’s row says how often Noon told its agent something recently. The agents and you work from the same facts.

What would change our mind #

Our runs were short. In real tasks lasting minutes, the second agent would more often see the first one’s change before choosing, which is where facts did sometimes help. If longer tasks on real repositories showed notes changing nothing, or showed claims paying for the parallel work they cost, we would revisit this.

The larger gap is changes that merge cleanly and still break each other. In the Django study above, a message describing the other, finished change recovered 82% of runs (89 of 108). The benchmark wrote that message from the known change, and the authors say plainly: "We do not evaluate messages generated during ongoing work." [20] It suggests telling an agent what another change did, not only which files it touched. Whether that holds outside a benchmark, we don’t know yet.
